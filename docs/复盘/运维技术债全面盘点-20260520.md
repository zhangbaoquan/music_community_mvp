# 二、🔴 严重问题（必须立即处理）

## S-01：Sentry 监控形同虚设 — 生产环境零错误可见性

**文件**：[lib/main.dart:60](file:///Users/zhangbaoquan/Documents/Work/Porject/music_community_mvp/lib/main.dart#L58-L64)

**现状**：Sentry DSN 是一个占位符：

```dart
options.dsn = 'https://example@o0.ingest.sentry.io/0'; // Placeholder DSN: USER MUST REPLACE
```

v1.0 的 T17 任务集成了 Sentry SDK，但 **DSN 从来没有替换成真实的**。这意味着：
- 所有 Dart 层异常被 Sentry SDK 捕获后，发送到一个**不存在的端点**
- **生产环境没有任何错误监控**，用户遇到的 crash 和异常全部静默丢失
- 你不知道用户在遇到什么问题，除非他们主动告诉你

**修复成本**：⭐（5 分钟）— 注册 Sentry 免费账户，替换 DSN 即可

## R-04：无任何监控告警基础设施

**现状**：除了上面形同虚设的 Sentry，项目完全没有：

| 监控类型 | 状态 |
|---------|------|
| 站点可用性监控（Uptime） | ❌ 无 |
| 服务器资源监控（CPU/内存/磁盘） | ❌ 无 |

**影响**：网站挂了，你可能是最后一个知道的人。目前唯一的"监控"是用户给你发消息说"打不开了"。

**修复成本**：⭐⭐（30 分钟）— UptimeRobot 免费版可监控 50 个 URL，注册后添加 `https://qinqinmusic.com` 即可

## S-03：CORS 策略为 `*` 通配符 — 全站 API 对外敞开

**文件**：[nginx.conf](file:///Users/zhangbaoquan/Documents/Work/Porject/music_community_mvp/nginx.conf) — 行 104, 122, 130, 147, 154, 171

所有 Supabase 代理路径（`/storage/v1/`、`/auth/v1/`、`/rest/v1/`）的 CORS 配置均为：

```nginx
add_header 'Access-Control-Allow-Origin' '*';
```

**影响**：任何网站都可以向你的 Supabase 后端发起跨域请求。这是 CSRF 攻击和数据泄露的敞开大门。

**建议**：改为 `add_header 'Access-Control-Allow-Origin' 'https://qinqinmusic.com';`

## S-04：缺少所有安全响应头

## S-05：启用了已废弃的 TLS 1.0 / 1.1

**文件**：[nginx.conf:36](file:///Users/zhangbaoquan/Documents/Work/Porject/music_community_mvp/nginx.conf#L36)

```nginx
ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3;
```

TLSv1.0 和 TLSv1.1 已被 RFC 8996 正式废弃，存在 BEAST、POODLE 等已知漏洞。所有现代浏览器均已放弃支持。

**备注**：当前 Nginx 只监听 80 端口（SSL 在 CDN 层卸载），因此这行配置实际上是**死代码**。但既然存在，就应该修正或删除，避免未来架构调整时引入安全漏洞。

**建议**：改为 `ssl_protocols TLSv1.2 TLSv1.3;` 或直接删除（当前无 SSL 监听）。

## R-01：部署零回滚机制

**文件**：[deploy.sh](file:///Users/zhangbaoquan/Documents/Work/Porject/music_community_mvp/deploy.sh)

当前部署流程：

```
flutter build web → rsync 直接覆盖 /var/www/html/ → 完事
```

问题：
- ❌ 部署前不备份旧版本
- ❌ 没有回滚命令
- ❌ 部署后没有健康检查
- ❌ 如果新版本有问题，网站就一直挂着

**影响**：一次坏的部署 = 网站宕机，直到开发者手动修复。

**建议**：部署前加一行 `cp -r /var/www/html /var/www/html_backup_$(date +%Y%m%d%H%M%S)`，并在 rsync 后加一个简单的 curl 健康检查。

---

## R-02：部署后无健康检查

**文件**：[deploy.sh:37-43](file:///Users/zhangbaoquan/Documents/Work/Porject/music_community_mvp/deploy.sh#L37-L43)

rsync 完成后仅检查 rsync 退出码，不验证：
- Nginx 是否仍在运行
- 网站 HTTP 是否可达
- Flutter 应用是否正常加载

**建议**：在脚本末尾加入：

```bash
# 健康检查
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" http://localhost)
if [ "$HTTP_CODE" != "200" ]; then
  echo "❌ 部署异常！HTTP 状态码: $HTTP_CODE"
  echo "考虑回滚: cp -r /var/www/html_backup_* /var/www/html"
  exit 1
fi
echo "✅ 健康检查通过"
```

# 四、🟡 中等优先级问题

## S-06：无 HTTP → HTTPS 强制重定向

Nginx 只监听 80 端口，依赖 CDN 做 SSL 卸载。如果有人绕过 CDN 直接用 IP 访问，流量是明文的。当前 VPC 安全组已限制入站来源，风险可控但不理想。

## S-07：挖矿事件修复不彻底

安全事件复盘中提到的加固措施完成了核心项（关端口、锁 root），但以下**仍未执行**：
- ❌ SSH 未改为密钥登录（仍是密码，只靠 IP 白名单保护）
- ❌ 无 fail2ban 或入侵检测
- ❌ Docker 网络隔离未文档化
- ❌ 无灾难恢复计划

## P-01：未启用 Brotli 压缩

仅使用 gzip。Brotli 对 WASM 文件压缩率提升 15-25%，可直接减少 Flutter Web 冷启动时间。首屏优化复盘中标记为"🟢 低风险"但从未实施。

## P-02：未使用 `--wasm` 构建标志

`deploy.sh` 中的 `flutter build web` 未添加 `--wasm` 标志。Flutter 3.32+ 的 SkWasm 比 CanvasKit JS 更快，预计可减少冷启动 2-3 秒。同样在首屏优化复盘中标记但未实施。

## P-05：首屏优化后续项全部搁置

首屏优化复盘第七章列出的 4 个后续改进项，**全部仍处于 ⬜ 未开始状态**：

| 改进项 | 预估效果 | 状态 |
|-------|---------|------|
| `--wasm` 构建 | 冷启动 -2~3s | ⬜ |
| Brotli 压缩 | WASM 压缩率 +15-25% | ⬜ |
| Dart Deferred Loading | 减少首屏 JS 体积 | ⬜ |
| 本地字体完全替换 | 消除运行时字体网络请求 | ⬜ |

## R-03：Nginx 配置部署无备份

`deploy_nginx.sh` 用 `mv` 直接覆盖 `/etc/nginx/nginx.conf`，虽然有 `nginx -t` 语法检查，但语义错误（如错误的 proxy_pass）无法被检测。一旦出错，没有旧配置可恢复。

## R-05：无灾难恢复计划

没有文档化的流程来应对：
- 数据库备份 / 恢复
- 服务器从零重建
- Supabase 项目恢复
- Storage Bucket 数据备份

## M-02：SQL 无迁移策略

`sql/` 目录有 5 个文件，按功能命名而非版本序号。没有迁移运行器，没有 `migrations` 表追踪哪些已执行。v3.0 的 T21（RPC 聚合）会新增大量 SQL 文件，如果没有策略，将变得混乱。

## M-03：T19/T20/T21 运维相关任务全部未开始

| 任务 | 内容 | 状态 |
|------|------|------|
| T19 | 资源管道化（图片/音频压缩） | ⬜ |
| T20 | 游标分页 | ⬜ |
| T21 | Postgres RPC 聚合下放 | ⬜ |

## 与 DNS 复盘的呼应

好消息是：第 1 批修复只需要 ~2 小时，就能补上最关键的安全和监控缺口。这是 ROI 最高的 2 小时投入。

# 安全防线复盘：当 Docker 的“特权”撞上裸奔的敏感端口

> 一个移动端开发者在云服务器安全上交的“学费”，以及如何用一小时构建企业级 VPC 防火墙阻击挖矿木马。

---

## 一、背景：公测前夜的一枚“震撼弹”

亲亲心情笔记 MVP 版本在经历了首屏优化和路由重构后，本已做好了扩大公测的准备。由于团队是纯移动端背景，对后端和运维的认知停留在“能跑就行”的阶段，本着“重功能、轻安全”的 MVP 理念，打算等功能做完再统一处理安全问题。

然而，2026年05月11日深夜，腾讯云安全中心的一封红色告警邮件打破了平静：
- **高危告警**：服务器疑似被植入挖矿木马。
- **攻击实锤**：主机频繁连接某已知矿池 IP (207.180.232.206) 的 5557 端口，累计达 725 次。
- **并发攻击**：伴随 Laravel 与 React Server Components 的高频漏洞扫描。

这颗“雷”提前炸响，逼迫我们在公测前进行了一场极其硬核的实战演习。

## 二、核心问题剖析：为什么防线形同虚设？

在排查过程中，我们发现问题的核心并不是黑客使用了多么高深复杂的“零日漏洞 (0-day)”，而是由于开发者对 Linux 网络架构的认知盲区导致了“开门揖盗”。

### 2.1 致命的 Docker 网络“霸权”
在常规认知中，只要在 Linux 上配置了 UFW 防火墙关闭端口就万事大吉。但在实际运行 Supabase 时，Docker 的端口映射（例如 `0.0.0.0:3000->3000/tcp`）拥有直接修改 iptables 的最高特权，它会**强行穿透宿主机本地防火墙**，将端口暴露给全世界。

### 2.2 敏感服务“裸奔”与 RCE 注入
由于上述机制，Supabase 的内部管理面板 Studio（3000 端口）被直接暴露在了公网。黑客的自动化脚本扫描到了这个端口，并利用其无鉴权（或默认密码）的特性，直接通过 SQL Editor 执行了 PostgreSQL 的恶意指令（如 `COPY PROGRAM`），从而在容器内部触发了远程代码执行 (RCE)，下载并启动了挖矿木马。

### 2.3 随时可能被攻陷的 SSH
服务器的 22 (SSH) 端口对全网 (`0.0.0.0/0`) 开放。尽管本次木马从 3000 端口攻入，但在排查时发现 SSH 密码已被木马篡改（导致终端连入时报 `Permission denied`），暴露出 SSH 未绑明白名单的巨大风险。

## 三、破局之道：降维打击与全链路清剿

发现问题后，我们没有选择盲目在服务器内部用杀毒软件死磕，而是采取了“物理隔离 + 底层清剿”的策略。

### 3.1 第一步：云端物理防火墙（VPC 安全组）断网
放弃在服务器系统内部修改 iptables，直接登录腾讯云控制台，在**更高维度的 VPC 安全组**中：
- 将 3000 (Supabase Studio) 和 8000 (API Gateway) 端口的访问策略直接设为**拒绝**。
- 将 22 (SSH) 端口的来源限定为**开发者当前的家庭宽带公网 IP**。
*效果：瞬间斩断了黑客与服务器的外部联系，将自动化攻击脚本阻挡在云端路由器之外。*

### 3.2 第二步：夺回系统控制权
面对 SSH 密码被篡改的绝境，利用腾讯云控制台的最高权限：
- 强制重置 Root 密码并重启服务器实例。
- 重启操作不仅夺回了控制权，更重要的是**顺手清除了驻留在内存中的挖矿进程**。

### 3.3 第三步：地毯式排雷验证
通过 SSH 重新登入后，进行严密的交叉验证：
1. **CPU 负载验证**：执行 `top` 命令，确认系统闲置率高达 86%，无异常高占用进程。
2. **木马残留验证**：执行 `sudo crontab -l` 检查所有定时任务，仅发现官方的 `qcloud stargate` 监控，确认木马没有留下自启动后门。
3. **网络连接验证**：执行 `sudo netstat -anpt` 监听矿池 IP，输出为空，确认木马已死透。
4. **业务可用性验证**：执行 `sudo docker ps` 确认 Supabase 核心容器运行健康，本地 Flutter 客户端成功走 80/443 端口获取数据。

### 3.4 第四步：三天后的"定时炸弹" -- root 空口令后门

事件处理三天后（05月14日），腾讯云基线安全检测发出新的高危告警：**系统存在空口令账号，用户不用口令认证就能进入系统。** 展开详情后发现，空口令账号竟然是 `root` -- 服务器的最高权限超级管理员。

这揭示了黑客攻击链中极其阴险的一环：木马脚本在被植入的那几秒钟里，不仅启动了挖矿程序（驻留在内存中，重启即死），还同时执行了类似 `passwd -d root` 的命令，**将 root 密码从硬盘上的 `/etc/shadow` 文件中彻底清空**。这属于对持久化存储的篡改，不会因为服务器重启而恢复。

这里涉及一个关键的操作系统概念：**"进程"与"配置文件"的本质区别**。挖矿程序是一个运行在内存中的进程，重启服务器后内存清零，进程随之消亡。但清空 root 密码是对硬盘上 `/etc/shadow` 配置文件的修改，就像修改了一个 Word 文档并点击了"保存" -- 无论重启多少次，这段被篡改的记录都会永久保留在硬盘上。

黑客的意图非常明确：即使挖矿进程被重启杀死、即使 3000 端口被关闭，只要 22 端口（SSH）还对外开放，他随时可以用 `root` 账号、不输密码直接登入服务器，重新植入木马。

**但这个 "Plan B" 被我们在第一时间的一个"可选操作"彻底封杀了。** 还记得当晚修复安全组时，将 SSH 22 端口的来源绑定为开发者家庭宽带 IP 吗？当时这被认为是一个"锦上添花"的可选加固项。但正是这个看似不那么紧迫的操作，让黑客虽然手握 root 空口令这把"万能钥匙"，却连服务器的门都摸不到 -- 所有来自非白名单 IP 的 SSH 连接请求，在到达服务器之前就被 VPC 安全组丢弃了。

**修复方式**：执行 `sudo passwd -l root` 锁定 root 账号的密码登录能力，彻底封死这个后门。日常管理通过 `ubuntu` 账号 + `sudo` 提权即可。

## 四、沉淀与反思：安全不是奢侈品，是底线

### 4.1 转变思维：MVP 不等于“不设防”
独立开发者在做产品时，往往将全部精力倾注在“用户能看到”的端侧体验（UI、加载速度）上，而忽略了后端的基建安全。这次事件敲响了警钟：**安全并不是等产品做大了才考虑的“奢侈品”，只要 IP 暴露在公网，防御体系就必须是出厂标配。**

### 4.2 认清防线的层级边界
- **业务安全**（如 JWT、RLS 策略）防的是内鬼和越权操作，它工作在应用层。
- **基建安全**（如 VPC 安全组、SSH 密钥登录）防的是全球泛滥的自动化僵尸网络，它必须工作在物理或系统底层。
绝对不能用业务逻辑的健壮性，去替代网络端口的物理隔离。

### 4.3 纵深防御：可选项也要当必选项
root 空口令后门的发现，是本次事件中最深刻的教训。它完美诠释了安全领域的**"纵深防御（Defense in Depth）"**原则：永远不要只依赖单一防线。

当晚关闭 3000 端口是"止血"，锁定 SSH 来源 IP 是"可选的额外加固"。如果当时只做了止血就去睡觉，黑客的 Plan B（通过 root 空口令走 SSH 回来）会在几小时内重新攻陷服务器。正是那个"多做一步"的谨慎决定，无意中构建了第二道防线，让黑客的后手棋彻底失效。

**在安全问题上，能多加一层防御就多加一层。所谓"可选项"，只是技术文档在描述最低要求，但从实际风险的角度，它往往是"不能不做"的。**

### 4.4 因祸得福的成人礼
如果在公测爆发、积累了大量用户日记数据后再遇到此类勒索或挖矿攻击，后果不堪设想。在上线前夜提前排爆，只花了一个小时便永久解决了一项隐形技术债，同时让团队补齐了云运维（DevSecOps）的认知短板，这是最廉价也是最宝贵的一堂实战课。
